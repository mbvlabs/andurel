# Andurel 2.0 — First Release Candidate

> **Release candidate.** This is `v2.0.0-rc.1`, not the stable 2.0 release. Use it for new projects and evaluation, not for a production v1 upgrade. Breaking changes are still possible.

Andurel 2.0 rebuilds the framework around Go's standard library and an
agent-first workflow. It is still a full-stack Go framework: PostgreSQL, jobs,
authentication, email, and Inertia. HTTP is `net/http`, wiring is explicit Go,
SQL lives with the domain that owns it, and the CLI is built for an agent to
discover, edit, regenerate, and verify without handing code to a generator.

## Try it

```bash
go install github.com/mbvlabs/andurel/v2@v2.0.0-rc.1
andurel --version
andurel new rc1-smoke
cd rc1-smoke
andurel tool sync
pnpm install
cp .env.example .env
andurel email render --open   # first look, no database needed
```

To run the app, set the database values in `.env`, then create and migrate the database before starting the server:

```bash
andurel db create          # only if the database does not exist yet
andurel db migrate up
andurel run
```

`--ui vue/bun` and `--ui svelte/npm` use the same Go backend.

## What changed from v1

The baseline is the latest v1 release, `v1.5.5`: a Rails-like framework built on Echo, Uber Fx, Bun, and templ/Datastar, with Inertia optional. V2 keeps the full-stack shape and replaces the foundation.

### Agent-first CLI and project shape

V1 already exposed JSON output, command discovery, and a skill. V2 makes those
the organizing principle.

- `andurel commands --json` and `inspect ... --json` describe the CLI and
  project without parsing help text or reading every file.
- `andurel patterns` publishes read-only reference code, placement rules, and a
  checklist. Agents write ordinary Go from the pattern, not generated CRUD.
- `andurel sync` refreshes derived artifacts; `andurel verify` checks
  formatting, vet, layers, frontend typechecking, and generated drift, naming a
  fix for every violation.
- Structured commands share an `{ok, data, summary, breadcrumbs}` envelope,
  with `{ok: false, code, error, hint, exit_code}` on failure. `--json`,
  `--agent`, `--jq`, and `--md` select machine output.
- `andurel skill install --harness codex|claude|pi|opencode|crush` installs the
  bundled layer-placement, HTTP, CLI, and testing references.

### Go-native HTTP and explicit wiring

- **`net/http` instead of Echo.** `pkg/anduin` supplies routing, middleware,
  request helpers, and the server lifecycle; handlers are
  `func(context.Context) error`.
- **Explicit constructors instead of Fx.** `app/` is the composition root, one
  constructor per process, with no container or service locator.
- **A fixed layer map.** `domains/` owns business logic and persistence,
  `services/` cross-domain flow, `handlers/` HTTP adapters, `routes/` route
  data, `middleware/` policy, and `app/` wiring.

### Domains own their SQL

V1 used Bun as its default persistence layer. V2 uses narsilc and pgx:

- SQL lives in `domains/<entity>.sql` next to its domain, not in a central
  query directory or an opaque ORM call site.
- narsilc compiles it into `domains/internal/queries`, imported only by
  `domains/**`. Queries scan into caller-owned structs, not generated rows.
- `services/` coordinate domains; `storage.AtomicOps` with
  `storage.Transactor` is the commit boundary for multi-step writes.
- SQL migrations remain the schema history. `andurel verify` enforces layers
  and transaction boundaries.

### Inertia only, and no templ

V1 shipped templ/Datastar pages by default and made Inertia optional. V2 has one
frontend path:

- **Inertia v3 with React, Vue, or Svelte**, backed by Andurel's own
  `pkg/inertia` adapter and Vite.
- **A standard `html/template` root document** at `resources/root.html`, embedded
  and parsed by `resources/root.go`. templ is gone from pages, email, and build.
- **No server-rendered template page layer.** JSON endpoints are normal routes
  that return JSON; there is no separate API mode.

River jobs, authentication, sessions, and `andurel run` live reload remain in
the scaffold; they run on the new stack rather than being new in 2.0.

### Email

V1 authored email in templ with handwritten CSS and inline styles. V2 authors email as React Email TSX and renders it with Go:

- Components, shared theme, Go structs, and committed templates live in one
  `emails/` tree. `andurel sync emails` writes the props and manifest, then
  exports the TSX to committed Go `text/template` files.
- Go renders those templates through `pkg/postmand` at send time. Node is used
  for the export step, not for email rendering.
- `andurel email render [name] [--open] [--watch]` renders real HTML and text
  through the same Go path into `tmp/emails/`. It sends nothing.

### Generation without rewriting your app

V1's `generate model`, `controller`, `scaffold`, `factory`, `view`, `job`, and `email` commands wrote and merged application source. V2 removes them:

- `andurel generate migration` creates a migration file. It is the only
  `generate` command that writes into the application.
- `andurel new` produces one complete reference application, including
  authentication, jobs, email, and Inertia pages.
- Generated outputs are limited to declared derived files:
  `domains/internal/queries`, `resources/js/routes.ts`,
  `resources/js/types/payloads.ts`, and the generated email files. They are
  committed, owned by generators, and refreshed with `andurel sync`.
- `andurel upgrade` re-pins framework modules, synchronizes tools, and reports
  application-owned changes. It never rewrites application source.

A framework release cannot silently regenerate your application. That is what
"the code is yours" means in practice. `andurel build` compiles every process
(`app`, `queue`, `migrate`, `ssr`), Vite assets, and email into `dist/`.
Framework behavior lives in independently versioned `pkg/*` modules. V2 uses
the `/v2` module path, requires Go 1.27.3 or later, and supports Linux and macOS
on amd64 and arm64.

## Removed from v1

- Echo, Uber Fx, Bun, templ, Datastar, and server-rendered pages. UI selection
  is now `--ui` instead of `--inertia`.
- Application-code generators: `generate model`, `controller`, `scaffold`,
  `factory`, `view`, `job`, and `email`.

## Upgrading from Andurel 1

**There is no supported automated v1 to v2 migration.** The v2 CLI refuses to
upgrade across a major version, and `andurel upgrade` is not a v1 migration
tool. It upgrades v2 projects and never rewrites application source.

V1 applications stay on the `1-5-stable` branch with a v1 CLI. To evaluate 2.0
alongside one, keep the existing app on v1 (latest tag `v1.5.5`) and back up
the database before any schema or data work. Create a fresh v2 project with
`andurel new`, using the same Inertia adapter and package manager if you want a
comparable frontend. Port domain code, migrations, data, configuration, routes,
handlers, frontend pages, and emails by hand. Re-run generators that own derived
files, then run `andurel verify` and your tests before cutover. The port is
manual by design: the two architectures do not share application interfaces,
persistence types, or frontend build layout.
