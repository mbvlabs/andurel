# Andurel-Owned Inertia v3 Package

Build and adopt an Andurel-owned Inertia v3 server adapter that is native to Echo and uses templ for the initial HTML document. Replace Gonertia without changing Inertia into a separate application mode and without changing the existing per-response `WithSSR()` design.

## Status Key

- [ ] = not started
- [x] = complete

## Outcome

An Inertia application generated by Andurel will:

- Use an Andurel-owned Go implementation of the Inertia v3 server protocol.
- Continue using the official `@inertiajs/svelte`, `@inertiajs/vue3`, or `@inertiajs/react` client package.
- Integrate directly with Echo rather than adapting a generic `net/http` middleware.
- Render the initial HTML document with templ.
- Support client-side rendering by default and per-response SSR through `inertia.WithSSR()`.
- Keep Andurel responsible for starting, monitoring, and stopping the Node SSR runtime.
- Use backend-owned Go payload types as the source of truth for page data and generated TypeScript types.
- Allow existing generated controllers to migrate without a broad rewrite.

## Non-Goals

- Reimplementing or forking the Inertia browser client.
- Adding a new scaffold type for SSR.
- Making SSR an application-wide alternative to normal Inertia rendering.
- Adding Datastar streaming to Inertia pages in this work.
- Making a JavaScript Inertia component and a templ component share the same UI implementation.
- Supporting Laravel Precognition unless Andurel introduces an equivalent validation feature separately.
- Keeping Gonertia-specific behavior that conflicts with the Inertia v3 protocol.

## Design Principles

1. **Protocol compatibility comes first.** The official Inertia v3 protocol and Laravel adapter are the behavioral reference.
2. **Learn from Gonertia.** Preserve Gonertia's proven Go API ergonomics and implementation patterns wherever they remain compatible with v3 and Echo.
3. **Echo is the native transport.** The public request API accepts `*echo.Context`; no generic response-buffering adapter is required.
4. **The backend owns payloads.** Generated Go structs define page data. TypeScript declarations are derived from those structs.
5. **SSR is a response option.** `WithSSR()` remains an option passed to the normal page render call.
6. **Generated applications are self-contained.** The full protocol implementation is generated directly into each application's `internal/inertia` package. Application-specific sharing, Vite assets, and configuration live alongside it in the same package. No generated code imports an Andurel runtime package for Inertia.
7. **Do not expose incomplete v3 support.** Gonertia is removed only after the conformance matrix is complete.
8. **Avoid hidden concurrency.** Prop resolvers execute deterministically by default. Concurrency may be introduced later only through an explicit API.

## Current State

The current generated `internal/inertia` package wraps `github.com/romsar/gonertia/v3`. It owns two Gonertia engines, selects the SSR engine when `WithSSR()` is present, configures the HTML root template, shares request data, and exposes middleware and redirect helpers.

The current frontend templates use Inertia v2 client packages. Gonertia's Go module major version is `v3`, but its roadmap still lists Inertia 3 compatibility as unfinished. Therefore the migration must include both the server adapter and official frontend client packages.

The existing controller API to preserve is conceptually:

```go
return renderer.Page(
	etx,
	"Users/Index",
	props,
	inertia.WithSSR(),
)
```

## Gonertia as a Design Reference

Gonertia should be audited before implementation and used as a secondary reference alongside the official v3 protocol. The goal is not to rewrite working ideas solely for originality; it is to own and evolve an adapter whose behavior matches Inertia v3 and Andurel's Echo architecture.

Patterns to preserve or adapt where possible:

- A small renderer initialized once and reused by controllers.
- Familiar `Render`/`Page`, `Redirect`, `Location`, and `Middleware` entry points.
- `Props` as an approachable response-boundary abstraction.
- Functional options for renderer, page, prop, and SSR configuration.
- Static shared props and request-scoped shared prop providers.
- Lazy prop resolver types and validation error helpers.
- Central page-object construction before choosing HTML, JSON, or SSR output.
- Root-document asset and head injection hooks.
- An HTTP SSR gateway with graceful client-rendering fallback.
- Typed helpers for merge, deferred, once, scroll, and history behavior where the concepts remain valid.
- Clear separation between configuration-time options and per-response options.

Patterns to replace rather than copy:

- Generic `net/http` response buffering. Echo response state should be used directly and non-Inertia responses must remain untouched.
- Top-level-only partial prop filtering. Inertia v3 requires nested dot-path behavior.
- Older once-prop semantics that do not implement v3 client retention headers and metadata.
- Any page-object shape that omits v3 fields such as `rescuedProps`, `sharedProps`, `onceProps`, or `preserveFragment`.
- Redirect, fragment, version, or status behavior that differs from the official v3 protocol.
- A single globally SSR-enabled engine. Andurel keeps SSR opt-in on each normal page response through `WithSSR()`.

The audit should produce a short mapping for every relevant Gonertia type or method:

```text
keep unchanged | adapt for Echo/v3 | replace | intentionally omit
```

Whenever Gonertia, the official protocol documentation, and the Laravel v3 adapter disagree, the official protocol and Laravel adapter take precedence.

## Target Package Structure

The full Inertia v3 protocol implementation is generated into each
application's `internal/inertia` package, making the generated application
self-contained for Inertia. The Andurel repository keeps the implementation as
the template source (`layout/templates/inertia_*.tmpl`), not as an importable
runtime package. No generated file imports `github.com/mbvlabs/andurel/inertia`,
and generated `go.mod` files do not require the Andurel module for Inertia.

Generated `internal/inertia` layout:

```text
internal/inertia/
  constants.go          protocol header and event constants
  request.go            Echo request parsing and normalized request state
  page.go               v3 page object and metadata types
  props.go              prop constructors and resolver interfaces
  props_resolver.go     nested filtering and prop evaluation
  response.go           initial HTML and Inertia JSON responses
  middleware.go         Echo-native response and redirect behavior
  redirect.go           location, redirect, and fragment rules
  root.go               templ root document integration
  ssr.go                SSR interface and fallback policy
  ssr_http.go           HTTP implementation of the SSR renderer contract
  errors.go             typed protocol and SSR errors
  render.go             renderer construction and shared/flash wiring
  page_options.go       WithSSR and application page options
  root.templ            application HTML document
  vite.go               Vite development and production assets
  ssr_runtime.go        Node SSR runtime ownership
```

All files are framework-managed and regenerated on upgrade. `root.templ` and
`vite.go` remain the customization points for application-specific metadata and
asset handling; the generated-andurel version marker governs ownership the same
way it does for the rest of `internal/`.

## Public API Direction

The first release should preserve the existing facade and avoid forcing a controller migration:

```go
type Renderer struct {
	engine *andurelinertia.Renderer
}

func (r *Renderer) Page(
	etx *echo.Context,
	component string,
	props inertia.Props,
	opts ...inertia.PageOption,
) error
```

`Props` must no longer be a Gonertia alias. It becomes an Andurel type.

Plain page payloads should normally be backend-owned structs:

```go
type UsersIndexProps struct {
	Users []UserResource `json:"users"`
}

return renderer.Page(
	etx,
	"Users/Index",
	inertia.FromStruct(UsersIndexProps{Users: users}),
)
```

Advanced Inertia behavior is added at the response boundary rather than embedded into domain or resource types:

```go
props := inertia.FromStruct(UsersIndexProps{Users: users})
props.Set("statistics", inertia.Deferred(loadStatistics))
```

The final names are subject to an API review, but the following concepts are required:

- `Props` and `FromStruct`.
- `Always`.
- `Optional`.
- `Deferred`, including group and rescue behavior.
- `Merge`, `Prepend`, and `DeepMerge`.
- `MatchOn`.
- `Once`, including key, expiry, and force-fresh behavior.
- `Scroll`.
- `WithSSR`.
- `WithStatus`.
- `WithValidationErrors`.
- `WithHistoryEncryption`, `WithHistoryClear`, and `WithPreserveFragment` where appropriate.

Resolver callbacks should receive the active `*echo.Context` so applications can use request-scoped authentication, sessions, logging, and cancellation.

## Inertia v3 Protocol Scope

### Request Classification

- [ ] Distinguish initial document requests from `X-Inertia: true` visits.
- [ ] Parse `X-Inertia-Version`.
- [ ] Parse partial component, `only`, and `except` headers.
- [ ] Parse reset paths.
- [ ] Parse the validation error-bag header.
- [ ] Parse infinite-scroll merge intent.
- [ ] Parse once-prop keys already retained by the client.
- [ ] Preserve request cancellation through Echo's request context.

### Response Headers and Content

- [ ] Return a full HTML document for initial visits.
- [ ] Return the v3 page object as JSON for Inertia visits.
- [ ] Set `X-Inertia: true` only on valid Inertia page responses.
- [ ] Append `X-Inertia` to `Vary` without destroying other `Vary` values.
- [ ] Use the correct JSON and HTML content types.
- [ ] Guarantee that `props.errors` exists and is an object.
- [ ] Preserve application-specified status codes where the protocol permits them.

### Page Object

Support all mandatory fields:

- [ ] `component`.
- [ ] `props`.
- [ ] `url`.
- [ ] `version`.

Support all conditional v3 fields:

- [ ] `encryptHistory`.
- [ ] `clearHistory`.
- [ ] `preserveFragment`.
- [ ] `mergeProps`.
- [ ] `prependProps`.
- [ ] `deepMergeProps`.
- [ ] `matchPropsOn`.
- [ ] `scrollProps`.
- [ ] `deferredProps`.
- [ ] `rescuedProps`.
- [ ] `sharedProps`.
- [ ] `onceProps`.
- [ ] `flash`.

Conditional fields should be omitted when inactive unless the official client requires an explicit empty value.

### Prop Evaluation

- [ ] Resolve regular props on full visits.
- [ ] Always resolve `Always` props, regardless of partial filters.
- [ ] Skip `Optional` props on full visits and resolve them only when selected.
- [ ] Announce but do not resolve deferred props on full visits.
- [ ] Group deferred props correctly.
- [ ] Resolve selected deferred props during partial reloads.
- [ ] Convert rescued deferred failures into `rescuedProps` while preserving a successful page response.
- [ ] Emit merge, prepend, deep-merge, and matching metadata only for resolved props.
- [ ] Remove merge metadata for reset paths.
- [ ] Implement once-prop retention and expiration using `X-Inertia-Except-Once-Props`.
- [ ] Implement scroll metadata and merge intent.
- [ ] Allow compatible categories to compose on the same prop.

### Nested Partial Reloads

- [ ] Support JSON-tag-aware dot paths.
- [ ] Match a selected parent to its descendants.
- [ ] Match a selected descendant while retaining its parent structure.
- [ ] Apply `only` before `except` when both are supplied.
- [ ] Ignore partial filtering when the requested component does not match the response component.
- [ ] Apply nested rules consistently to deferred, optional, reset, and merge metadata.

### Redirects and Versioning

- [ ] Convert `302` to `303` after `PUT`, `PATCH`, and `DELETE` where required.
- [ ] Return `409` plus `X-Inertia-Location` for external/full location visits.
- [ ] Return `409` plus `X-Inertia-Redirect` for the v3 redirect behavior that requires a fresh Inertia GET.
- [ ] Preserve URL fragments according to the v3 rules.
- [ ] Handle empty successful responses using the documented back-redirect behavior.
- [ ] Perform asset-version mismatch reloads for eligible GET visits.
- [ ] Do not perform a version-mismatch reload for unsafe methods.
- [ ] Include the current version on version-mismatch responses.
- [ ] Ensure `409` control responses are not labeled as Inertia page responses.

## templ Root Document

The initial Inertia document will be an application-owned templ component containing:

- The document structure and application metadata.
- Vite development or production assets.
- Inertia-managed head output.
- The JSON page script required by Inertia v3.
- The client application mount element.
- SSR body output when `WithSSR()` succeeds.

Security requirements:

- [ ] Encode page data with `encoding/json`.
- [ ] Escape every `/` in embedded page JSON as required by the v3 protocol.
- [ ] Do not HTML-entity encode the JSON script body.
- [ ] Do not pass arbitrary page JSON through `templ.Raw`.
- [ ] Treat SSR head and body output as trusted only when returned by the configured local runtime.
- [ ] Apply SSR response-size limits and request timeouts.

The renderer should buffer the root component before committing the response. This preserves the ability to report an error if templ rendering fails. Streaming the initial Inertia document is outside this plan.

## Echo Middleware

The native middleware should be narrow and predictable:

1. Parse the Inertia request state before the controller runs.
2. Allow the controller and normal Echo error handling to produce a response.
3. Apply redirect/status corrections required by the protocol.
4. Handle version mismatch and empty responses.
5. Preserve session flash and validation behavior.

It must not buffer every response merely to reproduce Gonertia's generic `net/http` implementation. If post-handler response inspection is required, use Echo response status and committed state or an intentionally scoped writer only for Inertia routes.

Non-Inertia routes, file responses, API responses, and SSE responses must bypass Inertia-specific processing.

## Shared Props, Flash, and Validation

The application facade should support:

- Static shared props configured at startup.
- Request-scoped shared providers.
- Lazy shared values.
- Authentication and authorization data.
- Validation error bags stored in the existing request/session flow.
- Flash data emitted through the v3 `flash` page field.
- Identification of top-level shared keys through `sharedProps`.

Precedence must be explicit:

1. Framework defaults such as `errors`.
2. Application shared props.
3. Controller/page props.
4. Per-response overrides.

Page props should win over shared props except for protected framework fields. Conflicts involving protected fields must return a descriptive error.

## SSR

SSR remains part of normal Inertia rendering.

```go
return renderer.Page(etx, "Home", props, inertia.WithSSR())
```

Required behavior:

- [ ] `WithSSR()` opts in only the current response.
- [ ] Responses without `WithSSR()` never contact the SSR runtime.
- [ ] The renderer posts the final v3 page object to the managed Node renderer.
- [ ] Successful SSR supplies head and body content to the templ root.
- [ ] SSR failure is logged with component and URL context.
- [ ] Production defaults to client rendering when SSR fails.
- [ ] Development and verification can enable a fail-fast option.
- [ ] Health and shutdown operations use bounded timeouts.
- [ ] The runtime URL defaults to loopback and is configurable.
- [ ] Node runtime ownership remains in Andurel's existing runtime manager.

The implementation should expose an `SSRRenderer` interface so the protocol renderer does not own process management and can be verified with a deterministic fake.

## Migration Strategy

### Existing Generated Applications

1. Update the managed `internal/inertia` facade.
2. Add the Andurel Inertia dependency.
3. Replace Gonertia imports and aliases.
4. Convert the root document to templ.
5. Upgrade official frontend packages from v2 to v3.
6. Update client entry points and hydration behavior.
7. Preserve application shared props and renderer options.
8. Report any unsupported Gonertia-specific custom option with a manual migration instruction.

### Compatibility Window

During development, retain Gonertia only as the old implementation used by existing projects that have not run the migration. Do not expose a permanent user-facing engine selector. Newly scaffolded projects should move to the native package only after the full conformance gate passes.

### Removal Gate

Remove Gonertia from Andurel templates only after:

- Every required v3 page field and header behavior is covered by the conformance verifier.
- Svelte, Vue, and React generated samples complete the browser scenario matrix.
- SSR opt-in, fallback, health, and shutdown behavior are verified.
- Upgrade rendering produces a valid existing-project migration.
- Documentation no longer recommends Gonertia options.

## Observability and Diagnostics

- Use typed errors for malformed protocol requests, prop resolution, root rendering, and SSR failures.
- Include component, request method, URL, and prop path in errors where safe.
- Never include prop values or session data in logs by default.
- Emit structured SSR fallback logs.
- Make `andurel doctor` verify compatible Inertia client versions, templ generation, Node availability when SSR is used, SSR bundle presence, and runtime health.
- Provide a development-only protocol debug mode showing parsed request state and emitted page metadata without exposing payload values.

## Risks and Mitigations

### Incomplete v3 Semantics

The prop resolver is the largest compatibility risk. Mitigate it with protocol fixtures before generator adoption and do not label the package v3-compatible until the complete matrix passes.

### Unsafe Initial JSON

Incorrect script escaping can cause parsing failures or cross-site scripting. Use a dedicated page-script encoder with explicit fixtures for `</script>`, Unicode separators, HTML characters, slashes, and invalid values.

### Middleware Interference

Global response buffering can break files, APIs, and streaming. Scope protocol behavior to Inertia routes and use Echo response state instead of a universal buffered writer.

### Frontend Version Drift

The protocol and official client packages can evolve independently of Andurel releases. Pin compatible major/minor ranges, include them in `andurel doctor`, and update protocol fixtures before dependency upgrades.

### Breaking Existing Customization

Applications may use Gonertia options directly. Preserve the common generated facade, detect unsupported imports during upgrade, and require explicit manual migration rather than silently changing behavior.

### SSR Masking Failures

Production fallback can hide broken SSR. Keep fallback as the safe production behavior but support fail-fast verification and observable structured errors.
