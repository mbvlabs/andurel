## Implementation

- Removed `upgradeCommandsRun`, which inferred follow-up work from report state.
- Added actual domain execution provenance:
  - `layout/upgrade/command_recorder.go` records each attempted subprocess and
    whether it failed;
  - `GitAnalyzer` records every git command it actually runs, so a real
    `upgrade`/dry-run/current/repair reports the read-only
    `git status --porcelain` safety checks it performs;
  - failed attempts are reported as `<command> (failed)`, never silently
    upgraded to success;
  - `UpgradeReport.CommandsRun` carries the domain record and
    `cli/upgrade.go` copies it into `artifacts.commands_run` without inference.
- Structured upgrades still never run `go mod tidy` or `andurel tool sync`;
  `commands_run` contains only commands actually attempted. Read-only safety
  checks are not suppressed to satisfy dry-run wording.
- Added `upgradeFollowUps`, shared by real and dry-run structured responses:
  - `go.mod` replacement => `go mod tidy` warning and breadcrumb;
  - added/updated/removed tools => `andurel tool sync` warning and breadcrumb;
  - dry run phrases mutation/install follow-ups as proposed work that was not
    run while still recording its read-only git checks;
  - already-current/repair reports without module or tool changes add neither.
- Pending repair (`RepairAvailable` before `RepairApplied`) is treated as a
  proposal, not a completed mutation: the repair warning and `andurel upgrade
  --repair` breadcrumb come first, and tidy/tool sync are described as work
  proposed after that repair.
- Preserved the existing upgrade envelope, existing `andurel doctor` / `git diff`
  breadcrumbs and human-mode behavior. Human mode still syncs tool binaries
  automatically when tool versions change and keeps `go mod tidy` advisory.
- Documented that `ok: true` means the upgrade mutation succeeded, not that the
  project was built, tidied or had its tool binaries installed.

## B7-003 contract

- Added `TestVerifySkippedContentKeepsStructuredEnvelopeSemantics`: a verify run
  with no content manifest keeps the command-level envelope `ok: true`, while
  the content stage is `status: "skipped"`, `ok: false`,
  `not_applicable: true`.
- Documented in `docs/content-verification.md` that consumers must inspect the
  stage status; the schema and semantics are unchanged.
- This test passed before and after the T03 change (it pins existing behavior;
  B7-003 is not a behavior change).

## Review corrections (P2)

### P2-1 — real execution provenance

The first T03 cut hardcoded an empty `commands_run`. The reviewer correctly
noted that the real upgrader executes read-only `git status --porcelain` checks
through `GitAnalyzer.IsClean` even for dry-run/current/repair. Suppressing those
checks would weaken safety validation, so the fix records them instead:

- domain recorder captures actual attempts and marks failures;
- CLI mirrors the domain record;
- dry-run wording distinguishes no mutation/install work from read-only
  prerequisite checks.

Red command:

```sh

go test ./cli -run 'TestStructuredUpgradeReportsDomainCommandProvenance|TestStructuredUpgradePendingRepairUsesProposalWording' -count=1
```

A later domain case, `TestUpgradeReportRecordsFailedGitCheck`, pins that a failed
git check remains a failed execution in the report rather than disappearing.

### P2-2 — pending repair is a proposal

When `RepairAvailable` is true and `RepairApplied` is false, `ReplacedFiles`
describes planned repair content rather than an applied mutation. The initial
wording incorrectly said `go.mod pins changed`, then appended repair advice.
The corrected response leads with `andurel upgrade --repair`, calls the file and
tool changes proposed/not applied, and describes tidy/tool sync as work
proposed after that repair. The dedicated fixture covers `go.mod` plus a tool
change under pending repair.

same slice, so repeated dry runs accumulated commands and concurrent runs raced.

`GitAnalyzer`, then works on a copy of the upgrader. The shared `Upgrader` is

### P2-2 — failed execution provenance in structured errors

`runUpgrade` previously discarded the domain report when the upgrader returned
an error, so a failed real git check lost its recorded command. Structured
errors now preserve the report under data `upgrade` plus `commands_run`, while
still returning an error envelope (never a success envelope). Existing
`CLIError` metadata is copied and unsupported-upgrade fields (`from`, `to`,
`rebuild_version`, `legacy_markers`) are retained.

Coverage:
- real CLI fixture: project without `.git`, real `upgrade.NewUpgrader`, failed
  `git status --porcelain (failed)` recorded in structured error data;
- typed fixture: `UnsupportedUpgradeError` keeps code/hint/exit and all
  unsupported metadata plus report provenance.

