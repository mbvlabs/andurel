## B7-039 characterization

With `Tests: true`, the pinned Go/x/tools produce the synthetic test main with
this metadata (fixture module `example.com/repro`):

| Field | Synthetic main |
| --- | --- |
| `ID` | `example.com/repro/payloads.test` |
| `Name` | `main` |
| `PkgPath` | `example.com/repro/payloads.test` |
| `ForTest` | empty |
| `Dir` | the tested package directory, e.g. `<root>/payloads` |
| `GoFiles`/`CompiledGoFiles` | exactly one file under `GOCACHE` |
| cache-relative path | `<first two hex digits>/<64-hex action ID>-d` |
| source prefix | `// Code generated by 'go test'. DO NOT EDIT.` |
| imports | the tested package(s) as `_test` aliases |

`ForTest` and `Dir` are therefore not reliable discriminators. The old
`isSyntheticTestMain` required the one generated source to be outside the
project root. With an in-root `GOCACHE`, `Dir` still points at `payloads`, the
file is `.gocache-fresh/...-d` or `.cache/go-build/...-d`, and the generated
main imports `example.com/repro/payloads` (and the external test package). The
`payloads-import` rule then reports the generated file as project source.

`TestPinnedGoSyntheticTestMainUsesCacheDataArtifact` pins this metadata and the
actual cache artifact layout (`<cache>/<2 hex>/<64 hex>-d`) against the pinned
Go/x/tools. If the toolchain changes the layout, that test fails instead of
silently making the filter unsound.

## P2 review revision

Reviewer P2 correctly found that the first revision still equated cache
containment with cache provenance. When `GOCACHE` is the project root or an
ancestor, a real `payloads/runner.test/main.go` with the generated-looking
header and `net/http` import is inside the configured cache directory. Identity
+ containment + header would therefore have hidden genuine source and produced a
missing violation instead of the required one. The reviewer also found that
`pathWithinDir` checked lexical containment before resolving symlinks, so a
cache artifact symlink escaping the cache could be accepted.

The revision adds:

- actual Go cache artifact evidence: exactly two path components, a lowercase
  two-hex prefix directory and a lowercase 64-hex action ID ending in `-d`, with
  the prefix matching the action ID;
- resolved-path containment first, lexical containment only as the fallback when
  resolution is unavailable;
- regression coverage for `GOCACHE=<project root>` and
  `GOCACHE=<ancestor of project root>`, retaining the real `.test` main
  violation and an ordinary generated-file violation;
- a symlink-escape test and lazy `go env` seam tests for failure, empty,
  whitespace and `off` results.

No blanket `.test`, header or cache-directory filter was introduced.

## Implementation

`isSyntheticTestMain` no longer contains any project-root containment check. The
predicate is the conservative composite:

1. go/packages identity: `Name == "main"`, `PkgPath` ends in `.test`, exactly
   one `GoFiles` entry.
2. Build-cache lookup: the cache directory comes from `go env GOCACHE`, resolved
   lazily only when a candidate exists. `off`, empty or command failure means
   "do not filter", never "hide source".
3. Actual generated artifact evidence: the source is a Go build-cache data
   artifact at `<cache>/<2 hex>/<64 hex>-d`, not merely a file inside the cache
   directory. Ordinary `.go` source cannot match this layout, including when the
   cache is the project root or an ancestor.
4. Generated-source evidence: the artifact begins with the exact `go test`
   generated-main header.

`relativeWithinDir` resolves both the cache and source paths when possible and
requires resolved containment; lexical comparison is only the fallback. A
symlink whose artifact name is inside the cache but whose target escapes is
therefore rejected. A real project `.test` main with a generated-looking header
remains analyzable in every cache layout, and ordinary generated project files
are not filtered. Because the check is scoped to generated test-main identity,
ordinary `_test.go` source in same-package and external test packages is still
analyzed.

## Limits

- `GOCACHE=off` is rejected by Go 1.27 before package loading, so there is no
  supported cacheless layout to filter.
- If `go env GOCACHE` fails, the loader conservatively analyzes the candidate
  rather than discarding source; that can surface a false positive but cannot
  hide real project code.
- The cache-artifact predicate is tied to the pinned Go cache layout. The
  pinned-metadata test makes a toolchain layout change a visible failure.
- The fresh-cache matrix intentionally compiles standard test dependencies from
  scratch; focused runtime is about 45 seconds and the full layers package about
  80 seconds. Duplicate fresh-cache runs were limited to the clean matrix;
  root/ancestor negative controls use their own two fresh layouts.
- Local workspace evidence only; no published-pin or release gate is claimed.
